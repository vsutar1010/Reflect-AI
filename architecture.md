# ReflectAI — Architecture Documentation

> **Purpose:** System design overview, data flow diagrams, API pipeline, AI architecture, and tech decisions for ReflectAI. Feed this file to any AI to understand HOW the system works end-to-end.
> **Last Updated:** 2026-09-04

---

## What is ReflectAI?

ReflectAI is an AI-powered "digital twin" platform. It builds a personality profile of a real person — either by interviewing them through 10 natural-language questions, or by importing a real WhatsApp chat export — analyzing how they communicate (vocabulary, punctuation, emoji usage, sentence length, Big Five personality traits, etc.) with a local LLM (Ollama). That profile is then used to power a chatbot ("digital twin") that talks like them, by text or live voice call. A separate Reflect/journaling feature lets a user write entries about themselves and get an AI-generated reflection back.

**Core value proposition:** Text chat and analysis LLM inference run fully locally via Ollama. Voice chat uses Vapi (cloud) for speech-to-text and text-to-speech; by default the reply itself is also generated by a hosted model via Vapi (`vapi-native` mode) because a CPU-only local model is too slow for a live call — a `custom-llm` fallback mode that routes voice through the same local Ollama is kept fully working for privacy-sensitive/offline use. Accounts, profiles, and conversation history are stored in MongoDB (Atlas or self-hosted), not on the local machine — see [Data Model](#data-model).

**LLM:** Ollama running `mistral:7b-instruct-v0.3-q3_K_S` locally by default (configurable via `OLLAMA_MODEL`).

## Request Flow: Authentication

```
Signup (email/password):
  Frontend Signup.jsx → POST /api/auth/signup/request-otp { email, password, name }
  Backend: generic 200 response regardless of whether the email is new,
    already registered, or on resend cooldown (prevents account
    enumeration — see auth_service/email_service). For a genuinely new
    email: generates a 6-digit OTP, emails it via SMTP, stores a
    pending signup in memory (expires after OTP_EXPIRE_MINUTES).
  Frontend → POST /api/auth/signup/verify-otp { email, otp }
  Backend: on match, creates the user in MongoDB `users`, sets the
    session cookie, returns the user.

Signup (Google):
  Frontend → POST /api/auth/google { credential }  (Google Identity Services ID token)
  Backend: verifies the token against GOOGLE_CLIENT_ID, finds-or-creates
    the user by google_sub (linking to an existing email if one
    matches), sets the session cookie.

Login:
  Frontend Login.jsx → POST /api/auth/login { email, password }
  Backend: rate-limited per client IP (5 failed attempts / 15 min,
    429 + Retry-After past that). Looks up the user, verifies the
    password with bcrypt — using a dummy hash when the user doesn't
    exist or has no password (Google-only account) so timing doesn't
    reveal which case it was. Nonexistent email / wrong password /
    Google-only account all return an identical 401.

Every subsequent request:
  Browser sends the httpOnly session cookie automatically (credentialed
  fetch). Backend's get_current_user dependency decodes the JWT, loads
  the user from MongoDB, and every route that touches a profile,
  conversation, or reflection filters by that user's id.
```

## Request Flow: Personality Analysis (Interview)

```
POST /api/analyze/start        → { session_id, message: <first question> }
POST /api/analyze/message      → { question, progress }   (repeat per answer)
POST /api/analyze/finalize     → { profile_id, profile }

Backend (analyzer.finalize_analysis):
  1. CommunicationAnalyzer.analyze(all messages) → rule-based fingerprint
  2. CommunicationAnalyzer.build_llm_prompt → prompt for Ollama
  3. OllamaClient.chat(temp=0.2) → JSON: personality (Big Five,
     0-100 score + description per trait), thinking pattern,
     emotional style, interests, summary
  4. build_identity_prompt(communication, personality) → system prompt
  5. Insert into MongoDB `profiles`, owned by current_user["id"]
```

## Request Flow: WhatsApp Import (alternative to the interview)

```
POST /api/analyze/whatsapp/upload   (multipart file)
  Backend: rejects non-.txt files; reads the upload in 1MB chunks and
    aborts with 413 the instant the running total exceeds
    MAX_WHATSAPP_UPLOAD_SIZE_MB (default 15) — never materializes an
    oversized file in memory. Parses participants + message counts.
  → { upload_id, participants, total_messages, ... }

POST /api/analyze/whatsapp/finalize  { upload_id, target_sender, profile_name }
  Backend: runs the picked sender's messages through the same
    CommunicationAnalyzer + Ollama pipeline as the interview flow,
    saves a profile the same way.
```

## Request Flow: Twin Text Chat (streaming)

```
Phase 1: Start Session
  POST /api/chat/start { profile_id }
  → { session_id, message: <opening_line>, history }
  (opening_line is built from communication stats — no LLM call)

Phase 2: Chat Turn
  POST /api/chat/message { session_id, message }
  Request header `Accept: text/event-stream` → SSE streaming reply.
  Anything else → plain JSON { reply } (kept for non-browser callers,
  e.g. the eval harness).

  Backend (TextChatService.stream_chat / .chat):
    1. engine.append_message(profile_id, "user", msg) → persist to MongoDB
    2. engine.build_dynamic_context(last 5 user messages) → mood instruction
    3. _catch_up_summary() → folds any history that has scrolled past
       MAX_HISTORY (20) into the running AI-generated summary (see
       Conversation Memory below) — cheap no-op if nothing new to fold
    4. engine.build_context_window(system_messages, history,
       dynamic_context, summary) → final message list
    5. OllamaClient.stream_chat(messages, temperature=0.6, max_tokens=60)
       → tokens yielded as SSE `data: {"delta": "..."}` frames, then
       `data: {"done": true}`
    6. engine.append_message(profile_id, "assistant", full_reply) → persist

  Frontend (Chat.jsx): renders each delta as it arrives, so the reply
  grows progressively instead of appearing all at once.
```

## Request Flow: Twin Voice Chat (Vapi)

```
Phase 1: Start Voice Session
  POST /api/voice/start { profile_id }
  → { session_id, public_key, assistant: <VapiAssistantConfig> }

  Backend (VoiceChatService.start_session):
    → loads twin context + history, builds opening line
    → writes the opening line to shared memory immediately (so Text
      Chat sees it even though voice hasn't said anything else yet)
    → build_assistant_config(): voice/transcriber config, firstMessage,
      and either:
        model: { provider: <vapi-native provider>, model: <...>,
                 messages: [<VapiPromptAdapter output>] }   (default)
        -- or --
        model: { provider: "custom-llm", url: .../api/voice/llm/{id} }

Phase 2: Browser Starts Vapi Call
  useVapiCall hook → new Vapi(public_key) → vapi.start(assistant_config)
  → Vapi Cloud handles STT + TTS + (vapi-native) the reply itself

Phase 3a: vapi-native mode
  This backend does not see per-turn traffic at all. What was said is
  learned only from the end-of-call-report webhook (Phase 4).

Phase 3b: custom-llm mode — per-utterance turn
  Vapi Cloud → POST /api/voice/llm/{session_id}/chat/completions
  Backend (VoiceChatService.stream_turn):
    1. Extract latest user utterance, append to shared memory
    2. build_dynamic_context(last 5 user messages)
    3. Read the persisted conversation summary (get_summary_state) —
       read-only on this path; TextChatService is what keeps it
       caught up, since both channels share the same conversation
       thread
    4. build_context_window(system_messages, history, dynamic_context,
       summary)
    5. OllamaClient.stream_chat(...) → tokens streamed back as
       OpenAI-compatible SSE chunks
    6. After stream: append full reply to shared memory

Phase 4: Call Lifecycle Webhooks
  Vapi Cloud → POST /api/voice/webhook, verified via a shared secret header
    - status-update (in-progress) → mark_call_started
    - end-of-call-report → mark session ended; in vapi-native mode,
      backfills the whole transcript into shared memory from the
      report (custom-llm mode already synced every turn live)

Phase 5: End Session
  Browser → vapi.stop(); POST /api/voice/end { session_id }
```

## Request Flow: Reflect / Journaling

```
POST /api/reflect { profile_id, content }
  Backend: saves the entry to MongoDB `reflections` FIRST (owner_id +
    profile_id scoped), then calls ReflectService.analyze(content) —
    an independent, single-shot Ollama call (no conversation memory
    involved). If analysis fails (Ollama down, bad JSON), the entry
    is still saved with analysis.status = "failed"; it never disappears.
  → { id, content, analysis: { status, mood, themes, reflection,
      observations, next_step } }

GET /api/reflect?profile_id=&limit=&skip=   → paginated list, owner-scoped
GET /api/reflect/{id}                       → single entry
PATCH /api/reflect/{id} { content }         → updates content, clears the
                                               stale analysis, re-runs it
POST /api/reflect/{id}/analyze              → re-run analysis ("try again")
DELETE /api/reflect/{id}
```

## AI Pipeline Detail

### Two-Layer Analysis Architecture (Interview / WhatsApp import)

```
Layer 1: Rule-Based (CommunicationAnalyzer)
  Word frequency, short forms, fillers, emoji, capitalization,
  punctuation, sentence length, greetings, bigrams/trigrams, response
  length style, vocabulary richness, typing habits — 15+ metrics,
  no LLM involved.

Layer 2: LLM-Based (Ollama)
  Big Five personality traits (openness, conscientiousness,
  extraversion, agreeableness, neuroticism — each a 0-100 score +
  short description), thinking pattern, emotional style, conversation
  behaviour, interests, human-readable summary.

Combined Output → identity_prompt
  A multi-paragraph system prompt injecting all of the above plus
  verbatim interview/chat quotes ("voice grounding") and behavioral
  rules. Stored on the profile document; built once at analysis time.
```

### DigitalTwinEngine — Shared Brain

Both `TextChatService` (text) and `VoiceChatService` (voice) use the same `DigitalTwinEngine` and the same MongoDB `conversations` document — this is what makes text chat and voice chat the **same digital twin** with continuous shared memory, not two separately-configured assistants.

### Conversation Memory & Summarization

```
Every turn:

  history[-20:]  (MAX_HISTORY)          ← always sent verbatim
       +
  running AI-generated summary          ← covers everything older than
  (conversations.summary field)           that, only if one exists
       +
  dynamic context (mood adaptation,     ← always injected
  last 5 user messages)
       +
  identity_prompt / voice grounding     ← always included, never dropped
       ↓
  sent to Ollama (or Vapi's hosted model, in vapi-native voice mode)

Summarization mechanics (TextChatService._fold_into_summary):
  - Runs every Text Chat turn. Computes how many messages have fallen
    outside the last-20 window (`summarized_through` cursor) and, if
    there's anything new, asks Ollama to merge it into the existing
    summary — never two competing summaries, one running note per
    conversation thread.
  - Stored on the same `conversations` document as `messages`
    (fields: `summary`, `summarized_through`, `summary_updated_at`).
    The raw `messages` array is never trimmed or deleted — only what's
    *sent to the LLM* is bounded, not what's stored.
  - If the Ollama call fails, the chat turn still succeeds using
    whatever summary already existed (or none) — summarization is a
    best-effort enhancement, never a hard dependency of a chat turn.
  - Voice's `custom-llm` mode reads this summary (read-only) on every
    turn; `vapi-native` mode doesn't use it the same way, since Vapi's
    hosted model isn't called per-turn by this backend at all (see
    Voice Chat flow above).
```

### Dynamic Context Adaptation

Every turn, after reading the last 5 user messages: energetic if the user seems excited, more serious if frustrated, jokes back if joking, analytical for technical questions. Never changes the twin's core writing style or personality — mood/energy/flow only.

## Data Model

### In-Memory State (not MongoDB)
Live interview/chat/voice **sessions** (the `session_id` → in-progress state lookup), and the login/OTP-request rate limiters, are per-process Python dicts — lost on a backend restart. This is distinct from profile/conversation/reflection *data*, which is always in MongoDB.

### MongoDB Collections

`users` — one document per account:
```
{ _id, email, name, password_hash (null for Google-only accounts),
  google_sub (sparse-unique, only set for Google accounts), created_at }
```

`profiles` — one document per twin, `_id` = profile UUID:
```
{
  _id, owner_id, name, created_at, last_used, version, voice,
  profile: {
    communication: { statistics, vocabulary, conversation_style,
                      writing_style, writing_patterns },
    llm_analysis: { personality: { <trait>: {score, description} }×5,
                     thinking_pattern, emotional_style,
                     conversation_behaviour, interests, summary },
    identity_prompt, generated_by, version
  },
  conversation   ← verbatim interview/WhatsApp transcript (source material)
}
```

`conversations` — one document per chat thread, `_id` = `"{profile_id}:{thread}"`, shared by text + voice:
```
{
  _id, profile_id, thread,
  messages: [{role, content, channel: "text"|"voice"}, ...],
  summary, summarized_through, summary_updated_at,
  updated_at
}
```

`reflections` — one document per journal entry:
```
{ _id, owner_id, profile_id, content, created_at, updated_at,
  analysis: { status: "pending"|"ready"|"failed", mood, themes,
              reflection, observations, next_step, error } }
```

## Tech Decisions and Rationale

| Decision | Why |
|----------|-----|
| Local Ollama for text chat + analysis | Privacy-first: that data never leaves the machine |
| DigitalTwinEngine shared by text + voice | Single source of truth for personality; prevents drift between channels |
| Adapters (`ollama_adapter.py`/`vapi_adapter.py`) separate from the engine | Prompt *formatting* per provider is a different, stateless responsibility from loading/caching profile + memory data — keeps the engine testable and makes adding a third provider additive, not a rewrite |
| `vapi-native` as the voice default | A CPU-only local model's time-to-first-token (10-90+s observed) is unusable for a live call; `custom-llm` stays as a fully-working configurable fallback for local-only/offline use |
| MongoDB storage | Profiles, conversations, users, and journal entries survive crashes/restarts; no file-based storage |
| Conversation summarization | Keeps LLM context bounded as a conversation grows, instead of either sending unbounded history or silently dropping old context forever |
| httpOnly session cookie + bcrypt + rate limiting | Standard session auth; login/signup enumeration and brute-force protections built in rather than left for later |
| React Context for auth + profiles | Avoids prop drilling; `ProtectedRoute` gates every twin-scoped page |
| Rolling context window (20 msgs) + summary | Keeps per-turn token count bounded and predictable even in a very long conversation |

## Current Limitations and Planned Extensions

### Active Limitations
| Limitation | Impact | Notes |
|------------|--------|-------|
| In-memory session/rate-limiter state | Lost on server restart; not safe for multiple backend processes without a shared store | Profile/conversation/reflection data is unaffected — that's all in MongoDB |
| `vapi-native` voice mode has no per-turn hook into this backend | This backend can't inject the persisted summary into a `vapi-native` reply the way it does for `custom-llm` | Vapi's hosted model only reports back via the end-of-call webhook |
| Voice-only conversations don't advance the summary themselves | Only `TextChatService` runs the summarization/folding step | Voice still reads whatever summary already exists |
| `custom-llm` voice latency | Multi-second-to-multi-minute replies on typical local CPU hardware | `vapi-native` (default) doesn't have this problem |
| Existing profiles may lack Big Five scores | Dashboard shows "not available yet" until re-analyzed | No automatic backfill/migration |
| Single default conversation thread per profile | `GET /api/profiles/:id/conversations` supports multiple threads architecturally, but only `"default"` is ever created today | Multi-conversation UI not built |

### Feature Roadmap (not yet built)
1. Shared session/rate-limiter store (Redis) for horizontal scaling
2. Per-profile Big Five re-analysis trigger (without a full re-interview)
3. Voice `vapi-native` incremental transcript sync (currently batch-synced at call end via webhook — see `voice-architecture-redesign.md` for the tradeoff analysis)
4. Multiple conversation threads per profile, surfaced in the UI
5. Profile rename functionality
